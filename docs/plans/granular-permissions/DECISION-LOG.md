# Decision log: Granular permissions

- **19-11-2026** On upgrade, groups that already have the AI section get every new AI right automatically. Rejected: treating "no rights ticked" as full access, because un-ticking the last right would suddenly grant everything.
- **19-11-2026** Prompts get the same "who can use it" limit as agents. Running a prompt only checks that someone is logged in, the same gap as agents.
- **19-11-2026** An agent or prompt with no groups chosen stays open to everyone, so existing sites behave the same after upgrade.
- **19-11-2026** Automate runs agents only if the workspace's service account may use them. The service account is the "who" for automations, not the person who built the automation.
- **19-11-2026** Ships on v17, v18 and v19. All three lines take features.
- **19-11-2026** In an automation step, the agent picker shows the service account's agents, not the editor's. A wrong choice is caught while building the automation, not only when it runs.
- **19-11-2026** If the service account loses access to an agent after the automation is saved, the step fails with a clear reason. Rejected: skipping it quietly, which hides the problem.
- **19-11-2026** The design must leave room to get more granular later without breaking anything: splitting an area right (for example "manage" into create, edit and delete), and rights on single items. For `feature-design`: name rights per area and action from the start, check them through one internal service rather than in each endpoint, and keep upgrade steps small and repeatable so a later split can grant the new rights to groups that had the old one. The CMS supports per-item rights for package entities through `IGranularPermission` and `IPermissionPresentationMapper` (seen in CMS v18 source; check v17 too).
- **19-11-2026** Brief guesses approved: one right per AI area (view-only for Audit log and Analytics), one right covers create, edit and delete, managers see every agent and prompt, and all three parts ship together.
- **19-11-2026** Ideas for `feature-design` from the investigation (not decided): use the CMS `entityUserPermission` manifest and the `Umb.Condition.UserPermission.Fallback` condition for area rights. Keep the agent group limit separate from the agent's Scope (Scope is where, this is who). Check the limit once in the agent and prompt services. Consider storing group aliases, not IDs, for Deploy. Automate: `RunAgentAction` already looks up the service account's groups and passes them in `AIAgentExecutionOptions.UserGroupIds`, so the new check can reuse them. When no service account is found, the user group list is null. The new check should then fail closed (refuse) for any agent that has a group limit.
- **19-11-2026** Area rights use CMS fallback permissions (`entityUserPermission` + `IReadOnlyUserGroup.Permissions`), checked on v17.8.2, v18.3.2 and v19.0.0-rc1. Rejected: our own rights table and screen, which would duplicate what the CMS user group screen already shows.
- **19-11-2026** Verbs are named `Uai.<Area>.<Action>` (for example `Uai.Connection.Manage`), so a later split into Create, Update and Delete only adds verbs plus an upgrade step.
- **19-11-2026** All checks go through one internal `AIPermissionService` in Umbraco.AI.Core. Management API writes use one authorization policy per right; agent and prompt limits are checked inside `IAIAgentService` and `IAIPromptService`.
- **19-11-2026** The agent and prompt limit is stored on the item, not as CMS granular permissions. Rejected: `umbracoUserGroup2GranularPermission`, whose foreign key to `umbracoNode` can't hold an agent's or prompt's key.
- **19-11-2026** User group keys are mapped by alias in Deploy, like the existing agent tool permissions. Built-in group keys are fixed across sites; custom group keys are random per site.
- **19-11-2026** A deleted user group stays in a saved limit and matches no one. Rejected: removing it on delete, which could turn a one-group limit into "everyone".
- **19-11-2026** Automate's step picker can know its workspace: Umbraco.Automate 18.5.0+ passes `workspaceId` into every field editor's config, and `IWorkspaceServiceAccountResolver` gives the service account. Publish checks use `IPublishValidatableStepType` (18.5.0+).
- **19-11-2026** Without an area right, the area's list and editor don't open from a direct URL either (workspace and collection manifests get the same condition). Rejected: showing it read-only. The read endpoints stay open for pickers.
- **19-11-2026** Changing an agent's or prompt's user group list follows the CMS's rule for assigning user groups: a non-admin can only add or remove groups they belong to, and only on an item they can already use. Rejected: Manage agents alone (a manager could give themselves any agent), and Users-section-only (a non-admin user manager could still add their own group).
- **19-11-2026** Build starts with three tasks at once: the core permission service (T1) and the new agent and prompt columns (T14, T28). Every other server task needs the permission service; the columns need nothing.
- **19-11-2026** Each wire task for the Agent and Prompt APIs (T22, T32) comes before its OpenAPI client is regenerated (T23, T33), since the client is generated from the running site.
- **19-11-2026** Agent and Prompt backoffice criteria are proven by the wire smoke tests, not Vitest. Neither frontend has a test runner, and adding one is out of scope.
- **19-11-2026** Rollback of an entity type with no mapped right is refused (plan guess 1), so a future add-on can't be rolled back by anyone with just the AI section.
- **19-11-2026** Cross-product floors are raised once, at the end (T43), because Agent, Prompt and Copilot Workspace reach the core permission service through `InternalsVisibleTo`, so they must never resolve an older Core.
- **19-11-2026** Ports to v17 and v19 wait until the v18 PR is approved (T45), and reuse the same migration IDs on every line.
- **19-11-2026** Pending specs are staged in `specs/` at their final repo paths, as earlier features did, because they name types that only exist once their task builds them. Each task moves its own specs into the real test project.
- **19-11-2026** Added to scope after planning: an agent's existing tool rules per user group follow the same rule as the new group list (SPEC R22). A non-admin only changes rows for groups they belong to. Rollback saves through the same check (R23), which also closes rollback as a way round R12. New story GP-18, tasks T46-T48. Rejected: a separate follow-up, which would leave two different rules for the two group settings on one agent.
- **19-11-2026** R22 does not stop a manager allowing extra tools for their own group, or adding tools to the agent's main tool list. Manage agents means trusted to choose an agent's tools; Umbraco's own tools still check CMS rights. Rejected: a separate "Manage agent tools" right (a 12th verb, about 3 more tasks) and admin-only tool changes. The `Uai.<Area>.<Action>` naming leaves room to add the split later.
- **24-11-2026** With no current backoffice user, `HasPermission` is false and the user has no groups and isn't admin. `CanUse` stays a pure method taking the group keys; `GetCurrentUserGroups()` supplies them. (feature-build, task T1, agent)
- **24-11-2026** Policy names follow `SectionAccessAI`'s style: `ManageConnectionsAI` … `ManagePromptsAI`, one per `AIPermissions` verb. - **24-11-2026** No hand-kept lists: each versionable adapter declares the right its rollback needs (`IAIVersionableEntityAdapter.RollbackPermission`, default null = refused), instead of a core map of entity types that every add-on would have to edit. Tests sweep controllers and adapters by reflection and convention (`Uai.<Area>.*` must match the controller's area namespace), with only small exception lists.
